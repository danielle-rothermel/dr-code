Function-Candidate Preprocessing & Corpus Analysis Plan

dr-code · 2026-07-19
This plan has two ordered parts. Part I updates dr_code.preprocessing so one exhaustive, function-oriented definition returns every valid candidate and directly records all semantic analysis facts. Part II assumes that flow exists and describes the corpus analysis we will perform from its traces. The parquet writer remains a thin persistence adapter: it attaches source identity and serializes pipeline-owned results without reclassifying them.

01

Update the preprocessing flow

The target is one exhaustive, directly labeled contract

Name the result rather than the heuristic

  • Register only humaneval-function-candidates@v1.
  • Export HUMANEVAL_FUNCTION_CANDIDATES_V1_DEFINITION.
  • Use version 1 because both the descriptive ID and output contract are new.
  • Preserve old traces as historical data, but do not keep definition aliases.

Make success and failure explicit

  • Success is a nonempty ordered candidate set.
  • Every survivor compiles and contains a top-level def or async def.
  • Failure is Absent with a stable failure_code, failed step, cause, and structured facts.
  • return_all replaces select_first.

The trace owns analysis semantics

Extraction provenance, stage counts, deduplication lineage, rejection codes, parser diagnostics, and function facts originate in preprocessing. Adapters may flatten them into columns, but may not infer new outcomes.

Function identity remains application policy

The filter requires a top-level function but never a particular name. Applications may add a name-aware step or filter preprocessing or test results. Executable tests determine task satisfaction.

Empty or whitespace-only response Usually classified before preprocessing Normalize, then emit decoder_output_blank from require_nonblank_text.

code = "def f(): ..." assignment Explicitly rejected Continue rejecting; measured corpus evidence did not justify decoding it.
XML tags, inline-backtick repair, speculative syntax completion Unsupported; no recurring, semantics-preserving rule was established Do not add without concrete recurrence, fixtures, and a safe recovery rule.
Make parser complexity a candidate-level failure before the full-corpus run. Python 3.13 can raise MemoryError: Parser stack overflowed for a sufficiently long operator chain. Convert only that specific parser-limit condition into a rejection; continue to re-raise genuine memory exhaustion.

Failure labels and facts are public preprocessing output

Extend the data-failure contract

Give StepFailedError a stable failure code and structured facts. Preserve the stable code on the compact Absent marker and the structured diagnostics in that step’s trace facts. A filter that removes the last candidate fails from that filter rather than passing an empty set to a generic final failure.

Use structured, JSON-valued facts

Replace string-only step facts with JSON-valued facts so lists of candidate origins, rejection records, counts, and AST summaries remain typed and directly serializable.

Preserve candidate identity through the flow

Assign a stable post-cleaning candidate_id and record the raw variant/strategy origins merged into it by deduplication. Rejection facts and later test results can then refer to the same candidate.

Emit structural facts where parsing occurs

Compilation and function filters already need the AST. They should emit parse/compile diagnostics, top-level function count, and function names; the corpus analyzer should not parse the source again.

Confirmed system findings define the implementation scope

Current fact Why it matters Required update
AlternativesStep stops after the first nonempty strategy. An unusable early result can hide useful later candidates. Use exhaustive ordered union with provenance, then deduplicate after cleaning.
select_first is structure-blind. It truncates both alternative candidates and later function-bearing candidates. Remove it from the named definition and finish with return_all.
filter_compilable accepts modules without functions. Compilation alone is weaker than the new output contract. Add filter_has_top_level_function after compilation.
The field-marker path is a separate definition and legacy strict parser profile. The marker is an input representation, not a distinct acceptance policy. Remove both identities and keep marker payload decoding in exhaustive extraction.
v2 collapses filter exhaustion into “no candidate survived filtering.” The final absence hides literal, representation, syntax, and structure failures. Emit stable codes and facts from the step that exhausts the set.
Two audited rows escape as parser-stack MemoryError. A data-shaped parser limit can abort an otherwise recoverable batch. Handle the exact parser-limit condition at every AST boundary.
run_preprocessing binds on every call. Registry resolution and settings validation repeat for 307,870 strings. Add a public bound runner now and reuse it across the corpus.
The definition hash omits bound implementation versions and source. Edited implementations can retain the same definition hash. Record commit, dirty/source hash, and resolved step versions in the run manifest.
ast_stats and code_test consume one CodeArtifact. Candidate-set output changes downstream wiring. Emit required AST facts in preprocessing; fan out successful candidates only at the later test boundary.
pyarrow is only available transitively through datasets. A direct PyArrow corpus writer should own its dependency. If the writer imports it, declare it directly with uv add pyarrow.

Implement and verify the redesign in four slices

1. Establish public contracts

  • Add the new definition ID, v1 definition, stable outcome codes, and JSON-valued facts.
  • Make success nonempty and failure directly labeled.
  • Remove field-marker and legacy strict identities without aliases.
  • Update exports, serialization, wiring tests, and permanent boundary documentation.

2. Make extraction exhaustive

  • Add raw, decoded JSON string, JSON code, and marker-payload variants.
  • Run every discovery rule, clean every candidate, and deduplicate with origin preservation.
  • Add blank, compilable, and top-level-function filters with candidate-level facts.
  • Turn the specific parser-stack limit into a recorded rejection.

3. Bind once and persist traces

  • Introduce the public bound-runner API and reuse it for all present strings.
  • Add a Typer CLI with explicit input, output directory, and batch-size options.
  • Serialize pipeline labels, facts, and candidates without semantic postprocessing.
  • Publish parquet and its manifest atomically.

4. Prove the new contract

  • Cover every outcome code and multi-candidate ordering/deduplication behavior.
  • Test blank input, JSON objects, marker payloads, async functions, and parser limits.
  • Assert every success is nonempty, compilable, and function-bearing.
  • Assert no present string escapes without a complete trace.

Every run gets an immutable manifest

  • Corpus path, SHA-256, schema, and expected row count
  • Serialized definition and definition hash
  • Git commit, dirty flag/source hash, and resolved step versions
  • Start/completion time, output rows, outcome totals, and completion state

Runs are append-only and publish atomically

Store runs under ../gen-viewer/data/preprocessing-runs/ with unique IDs. Write partial artifacts first, validate them, and publish only with complete: true. Never overwrite an earlier result set.

Everything below assumes humaneval-function-candidates@v1 is deployed, every present string has a complete authoritative trace, and the sidecar faithfully serializes those facts. We will query pipeline labels—not reconstruct them from raw outputs in the analysis job.

The analysis artifact is a thin, joinable trace projection

Adapter-owned identity

  • sample_id, run_id
  • decoder_output_presence
  • raw_output_sha256
  • One result row per source row

Pipeline-owned result

  • outcome_code or failure_code
  • failed_step, cause, propagated lineage
  • Per-stage counts and structured rejection records
  • Variant and strategy contribution

Pipeline-owned candidates

  • candidate_id, cleaned source, all origins
  • Parse and compile diagnostics
  • Top-level function count and names
  • Deduplication and ordering facts

The writer may mechanically flatten facts into typed columns and child tables. It must preserve the complete pipeline meaning and must not classify source text, parse candidates, or invent failure labels. Large repeated intermediate values may be retained only for a bounded diagnostic sample as long as every emitted fact and final candidate remains available.

Six analyses explain coverage, failures, and usefulness

1. Corpus and preprocessing funnel

  • Missing versus present decoder output
  • Blank, no candidate, filtered, and successful populations
  • Absolute counts and rates against both total and present-string denominators

2. Failure morphology

  • Terminal failure code and failed step
  • Syntax/compile error classes and parser-limit cases
  • Literal, code-repr, cleaned-empty, and no-function populations
  • Representative samples per stable code

3. Recovery-rule contribution

  • Candidate yield by text variant and discovery strategy
  • Unique recoveries attributable to JSON, marker, escaped, or Markdown rules
  • Rules that produce duplicates or only rejected candidates

4. Candidate multiplicity and ambiguity

  • Survivor count per output
  • How often multiple strategies converge on one cleaned candidate
  • How often candidates contain multiple top-level functions
  • Ordering and candidate-set changes between runs

5. Metadata-conditioned behavior

  • Outcome and rule contribution by model and source kind
  • Prompt, task, date, and fidelity slices
  • Concentrated failure modes that suggest targeted future rules

6. Extraction versus executable correctness

  • Fan every successful candidate into the applicable tests
  • Join test results by sample_id and candidate_id
  • Compare extractable, testable, passing, and failing populations
  • Do not impose a preprocessing-time function-name requirement

JSON-object decoding is the largest measured opportunity

  • 16,888 outputs are top-level JSON objects with a string code field.
  • Current best-effort fails on 12,543 of those objects.
  • Decoding the field and rerunning current extraction recovered a top-level function in 12,360 failures.
  • v1 provenance will measure exact unique recovery after every rule is exhaustive.

Marker decoding belongs in the general rule set

  • 56,363 outputs contain [[ ## code ## ]].
  • Current general extraction already succeeds on 55,643 of them.
  • Only 720 fail current best-effort; isolating the payload recovered one additional function.
  • v1 will measure marker contribution without maintaining a separate mode.
These baseline counts describe extraction and AST shape, not semantic correctness. Under the new flow, preprocessing supplies structural facts and stable candidates; executable tests supply behavioral evidence afterward.

The analysis run has explicit completion criteria

Data integrity

  • Exactly 365,216 sidecar rows and unique sample_id values
  • 57,346 missing external outputs and 307,870 preprocessing traces
  • 109 pipeline-labeled blank inputs
  • No unexpected per-input exceptions
  • Every success nonempty, compilable, and function-bearing

Analysis deliverables

  • Overall and metadata-sliced outcome funnels
  • Failure-code tables with deterministic review samples
  • Unique recovery and duplicate contribution by rule
  • Candidate multiplicity and structural summaries
  • v2→v1 transition report and candidate-level test-result join

The result is a reproducible separation of concerns: preprocessing owns all interpretation of decoder text and code candidates; the corpus job owns identity, persistence, and metadata joins; test execution owns behavioral correctness. That boundary lets us iterate on extraction rules and compare runs without rebuilding analysis semantics outside the official pipeline.
