Preprocessing Module Design

dr-code · 2026-07-13
Preprocessing turns uncontrolled input into trusted artifacts and shows its work. It stands alone: metrics, serving endpoints, dataset builders, and repair loops can all consume its traces. It is mechanical: declared steps, order, and settings; full retention; no silent guesses.

L1

Motivations & structural decisions

P-M1 · MOTIVATION
Uncontrolled model output requires robust recovery.
Model output varies unpredictably: fences, prose, escaped newlines, truncation, and smart quotes. The system robustly turns likely code into typed artifacts without enumerating every input shape.
P-M2 · MOTIVATION
Ambiguous repairs fail instead of changing code meaning.
A visible failure is safer than a repair that might change meaning. Ambiguous cases fail instead of guessing; for example, escaped-newline recovery preserves ambiguous escapes rather than mutating candidates.
P-M3 · MOTIVATION
Traces explain every preprocessing outcome.
The output alone must explain what extraction did and why, without reruns or log searches. Therefore the trace retains everything.
P-M4 · MOTIVATION
Reusable steps compose across product contexts.
The same context-free steps serve eval flows, /explain, synthetic datasets, and future repair loops through different compositions.
P-S1 · STRUCTURE
Step types determine pipeline input and output shapes.
Each step declares input and output types; composition determines the pipeline's shape. Pipelines can begin with raw generations or skip text handling and begin with asserted code.
P-S2 · STRUCTURE
Candidate fan-out remains data inside a linear pipeline.
Extraction produces a set-typed artifact. Steps operate on sets or their elements; a normalizer reduces a set to one value. Pipelines never branch or create per-candidate sub-pipelines.
P-S3 · STRUCTURE
Explicit deterministic settings eliminate hidden judgment.
Steps run in declared order with explicit settings. No adaptation, quality judgment, or hidden defaults change behavior. The definition fully describes the pipeline.
P-S4 · STRUCTURE
Traces retain every intermediate step output.
Every step output is returned, enabling later measurement of any intermediate without rerunning the pipeline.
L2

One layer down

Ordered fallbacks remain inside a single step.

  • Fallbacks—such as JSON, fenced-block, then escaped-newline extraction—are ordered, first-success alternatives within one step, not pipeline branches.
  • Order them conservative to aggressive. Use the first successful repair and record it in the trace.
  • Only two compositions exist: pipeline sequences and step-level alternatives. Both are mechanical.

Output-shape controls do not choose by quality.

  • select_first and return_all mechanically fix the output shape.
  • Quality-based selection requires cross-candidate metrics and belongs in caller policy, never preprocessing.

Stable step names become trace namespace keys.

  • Each step instance has a stable name, allowing repeated components. These names become trace keys alongside input and output.
  • Names are part of the definition and consumer contract, so renaming creates a new definition.

Step failures propagate as causal Absent values.

  • A failed step records Absent with a cause. Dependent steps propagate that cause, so the pipeline completes with a full trace.
  • Refusal and failure appear as data: an absence with a reason.

Steps may record facts but cannot apply quality policy.

  • Steps may record facts—AST parse results, candidate counts, or the chosen alternative—as provenance.
  • A step may describe its output, but may not prefer one output for its quality.

Synthetic corruptions provide adversarial recovery tests.

  • Synthetic corruptions mirror recovery steps: add/strip fences, add/strip annotations, inject/normalize smart quotes. They create what preprocessing must undo.
  • Give every recovery step matching corruption recipes, making the synthetic dataset a standing adversarial test corpus.
L3

Details

Steps declare identity, settings, types, and deterministic behavior.

  • A step has a name and version, frozen settings, declared types, and a deterministic apply. The same settings and input always produce the same output, without RNG, ambient state, or clocks.
  • Canonical outputs are serializable; rich views such as parse trees must be recomputable from them.
  • Definitions are ordered, named step instances and settings that are frozen, serializable, and hashable.

The corruption architecture provides the step-system template.

  • Mirror the existing corruption design: uniform interface, named-component registry, frozen recipes, and a simple fold runner like apply_recipe.
  • Reuse the registry↔enum sync test so the step vocabulary cannot drift.

Existing modules map directly to typed steps and definitions.

  • text_transforms / text_analysis → total, deterministic text steps.
  • code_transforms / import_inference → code-typed steps.
  • The code_parsing ladder → alternatives step; profiles → named frozen definitions; its trace → this design's general trace.
  • parsed_code-style structures → derived views over canonical source text.

Round-trip tests verify semantic recovery.

  • Primary property: round trips. Corrupt known inputs, then require preprocessing to recover semantic equivalence. Extend the synthetic suite into a standing contract test.
  • Test steps through their interface, definitions through the runner, and traces through their serialized projection—not step internals.
  • Assert canonical artifacts and absence causes, not internal decision-tree shapes.
