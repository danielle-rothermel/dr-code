Full Eval Flow: Boundary Design

dr-code · 2026-07-13
Eval flows comprise two independent systems and a thin contract. Preprocessing turns input into a trace; metrics extraction turns a trace-shaped value into records. Running them together is convenient, not architectural. This document covers only their shared contract and should remain the thinnest of the three.

L1

Motivations & structural decisions

M1 · MOTIVATION
Definitions and outputs explain themselves.
Definitions state what will happen; traces and records show what did. Each is self-describing, so provenance survives across experiments, dashboards, and training loops.
M2 · MOTIVATION
Definitions provide deterministic identity.
For each system, the same definition and input produce the same output. Frozen, serializable definitions identify sweeps, reproductions, and cross-run comparisons. Records carry the full provenance chain.
M3 · MOTIVATION
APIs organize concepts by meaning.
APIs follow meaning—a transform to apply or a question to ask—not implementation. Semantic configuration keeps integrations understandable.
S1 · STRUCTURE
Preprocessing and metrics remain independent.
Preprocessing and metrics extraction are independently usable, definable, and versioned. Run them together or preprocess once and measure later. Each knows only the trace.
S2 · STRUCTURE
The trace is the shared interface.
The trace is the sole shared interface. Preprocessing and external systems may produce it; metrics and external systems may consume it. Its shape therefore evolves carefully.
S3 · STRUCTURE
Canonical artifacts serialize; derived views recompute.
Every canonical artifact is serializable. Non-serializable views, such as ASTs, must be recomputable caches. Serialization may lose warm caches, never information; otherwise the design is invalid.
S4 · STRUCTURE
Metrics consume traces without feedback.
Metrics consume trace-shaped values and return records, with no channel back to preprocessing or other metrics. Decoupling makes the system a pipeline rather than a workflow graph.
S5 · STRUCTURE
Callers own scoring and selection policy.
Transforms produce state; metrics produce information; scores apply caller policy to that information. Scoring, filtering, and selection remain outside the library.
L2

The contract, one layer down

Traces expose a flat named artifact namespace.

  • A trace exposes a flat namespace of named values. Producers publish names (step-instance names in preprocessing); metric operators read keys and validate types.
  • This is an intentional placeholder. Design typed bindings after real usage reveals the shape, and introduce them explicitly.

Every trace reserves input and output.

  • Every trace carries its original input and final output, regardless of producer or steps.
  • Metrics bound to these keys work with any producer. Only intermediate measurements need instance names.

Missing keys are wiring errors; Absent values are data.

  • Missing key means incompatible definitions: throw at bind time.
  • Present-but-Absent means data failure: an Absent sentinel identifies the failed step and cause. Consumers emit not-applicable records.
  • This sharp runtime distinction compensates for the wiring checks lost with dict[str, Any].

Traces and records preserve full provenance.

  • A trace identifies its producing definition, or external if built outside dr-code.
  • A record adds its metric definition identity, preserving what computed it, on what, and how the input was produced—even after serialization.

Persisted traces support repeatable later measurement.

  • Persisting a trace for later or repeated measurement is a primary use case.
  • Deserialized traces have cold caches; derived views are recomputed from canonical artifacts. Results must match a fresh trace.
L3

Details

Serialized traces retain all canonical information.

  • A serialized trace contains canonical artifacts, names, lineage, causal absences, and provenance. It omits derived views.
  • Definitions, records, and serialized traces use BaseModel for persistence and external schemas. In-flight values use frozen dataclasses.

Operators validate the temporary dictionary contract.

  • Operators read declared keys, validate types, throw on wiring mismatches, and emit not-applicable for Absent.
  • There is no binding layer, typed views, or automatic resolution. Any replacement must reflect real usage and be a versioned boundary change.
