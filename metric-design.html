Metrics Extraction Module Design

dr-code · 2026-07-13
Metrics extraction asks artifacts versioned, stable questions and returns one comparable, self-describing answer per question. It is opinion-free, hides execution cost, and accepts artifacts from any source. dr-code preprocessing is convenient, not required.

L1

Motivations & structural decisions

X-M1 · MOTIVATION
Metric records support comparison across runs.
Metric records matter only in comparison across models, runs, time, and preprocessing definitions. Every design choice preserves safe comparability.
X-M2 · MOTIVATION
Metric semantic changes require new versions.
Silent computation changes invalidate comparisons. A metric's semantics therefore belong to its identity; changing them requires a new version.
X-M3 · MOTIVATION
Metrics report facts; callers define quality.
The system reports facts—lengths, ratios, parse outcomes, pass counts—not what is good. Callers can compose these neutral records into any policy.
X-M4 · MOTIVATION
Operators declare questions; the engine manages cost.
Callers declare questions, not execution plans. Cheap counts and costly container tests use the same interface; the engine manages cost.
X-S1 · STRUCTURE
Every declared question produces one record.
Every declared question yields exactly one record, including failures with causes. Declarations fully determine rows, so consumers never handle missing ones.
X-S2 · STRUCTURE
Metrics accept traces from any producer.
The system accepts any trace-shaped artifact namespace. Fresh, restored, and externally built inputs are equivalent and must produce the same results.
X-S3 · STRUCTURE
Flat self-describing records load directly into dataframes.
Records are flat, self-describing dataframe rows containing metric identity and version, input lineage, values, and any absence cause. Analysis tools need no system-specific code.
X-S4 · STRUCTURE
One engine coordinates all expensive computation.
One engine sees all questions before performing expensive or effectful work, especially code execution. Operators declare promises; the engine handles mechanics.
L2

One layer down

Bind-time errors identify incompatible definitions.

  • Under the placeholder contract, operators read declared keys and validate their types.
  • Missing key or wrong type ⇒ bind-time error: the definitions are incompatible.
  • Absent with cause ⇒ not-applicable record: upstream failed for this input, and the record preserves causal lineage.

Every record carries a value or causal absence plus provenance.

  • Every record contains metric identity and semantics version, input lineage keys, trace provenance, and either values or a causal not-applicable marker.
  • It identifies what computed it, at which version, on what, and how the input was produced.

Operators group related questions without merging semantics.

  • Questions include text and code statistics, parse and compile outcomes, compression ratios, and execution results. Shared machinery does not merge distinct questions such as code_test and code_stats.
  • Each cluster declares parameters, such as compressors or statistics, as part of its metric identity.

The engine collects questions before planning shared work.

  • The engine collects all questions before computing, allowing shared derived views, batched code execution, and cached-result reuse.
  • The same machinery rebuilds derived views for restored traces; a cold cache simply requires work.

Results depend only on canonical artifacts and the metric definition.

  • Results depend only on canonical artifacts and metric identity and settings—not derived views, caches, scheduling, or trace freshness.
  • Measuring a restored trace later must equal measuring the fresh trace now.

Metrics report observations; callers apply judgments.

  • In bounds: counts, ratios, distributions, outcomes, and per-candidate values over set-typed artifacts.
  • Out of bounds: thresholds, weights, verdicts, rankings, and "best". Callers derive these from records.
L3

Details

Measurement failures are typed records, not exceptions.

  • The system is total: measurement failures become data, never boundary-crossing exceptions. Wiring bugs remain bind-time errors.
  • An Absent input yields not-applicable with causal lineage, distinct from a measured zero.
  • An operator failure on present input yields a typed failure attributed to the metric, making measurement bugs visible.

Four engine promises define output reliability.

PromiseMeaning
Determinismsame canonical inputs + same metric identity/settings ⇒ same record
At-most-once executioneach candidate executes once per engine-cache lifetime, including cross-run sweeps via content hash
Totalityone record per declared question, absence and operator-failure included
Provenanceevery record identifies its metric version, input lineage, and trace producer

Injected runners and content-hash caching centralize execution.

  • The sandbox runner is an injected engine dependency, never an operator dependency. Production uses the OCI sandbox; tests use a local runner.
  • Cache keys combine canonical artifact hash, computation identity, and settings for within-run and cross-run reuse.
  • Use one runner session per batch where possible, preserving fail-closed behavior, kill attribution, and output bounds.

Existing metrics, sandbox, and scoring code map onto the new boundaries.

  • metrics.build_metrics_payload families and compression → operator clusters; their payload models inform record anatomy.
  • task.run_subprocess_batch + sandbox → the engine execution path behind code_test.
  • scoring.score_humaneval_submission → caller policy over records, retaining its outcome taxonomy.
