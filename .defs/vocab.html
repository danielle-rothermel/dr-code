The dr-code code-evaluation contract

A reference for the terms and guarantees that bind dr-code.

dr-code · 2026-07-24

This is the vocabulary of the code-evaluation contract dr-code implements: the terms, the guarantees that bind this repo, what is in and out of scope, and the mapping from each term to the names exported by dr_code.eval.

Terms

TermDefinition
DefinitionA versioned template that declares assignable variables and their constraints and produces one or more configs from them. It is the sole owner of its namesake config: a config is only ever built by assigning that definition's variables.
ConfigA complete validated instance built by assigning every required variable of exactly one definition. It carries a typed reference back to its owning definition plus its own identity hash.
VariableOne declared assignable slot on a definition, with optional allowed values and an optional default; a variable with neither is required and unconstrained.
MaterializeThe single operation that builds a validated config from a definition: assigning every required variable, filling defaults, and rejecting unknown, missing, or out-of-range values.
PayloadThe complete collection of fields that determine an object's identity, selected as finite JSON-safe data with no runtime or storage state; the input to an identity hash.
LineageThe chain of provenance and version references a value carries, so a measured value traces back to the exact operator, step, and config that produced it.
UnitThe explicit measurement unit a measured value must carry; an empty unit is rejected.
Zero-DenominatorThe explicit state of a ratio whose reference length is zero, represented by a declared sentinel and kept distinct from a value of zero.
Identity HashThe full 64-character lowercase SHA-256 hash of the canonical identity JSON of a definition or config payload.
Variable SpecThe declared form of one variable: its name, its allowed type or values, and whether it is required, resolved against an assignment when a definition is materialized.
Definition ReferenceA typed reference to an owning definition, carrying that definition's schema name, version, and identity hash, so a config names the exact definition and identity it was materialized from.
TaskA dataset-specific unit of work with a stable identity that supplies the generation inputs, evaluation inputs, and reference material an evaluation consumes.
HumanEval TaskA dataset-specific task with validated HumanEval fields and a stable identity over its dataset-defining fields, computed here as a task identity hash.
Task SetA versioned manifest holding either an ordered collection of dataset-specific task identities or a deterministic selection rule, plus a dataset revision, where the ordering and selection semantics all determine its identity.
RepeatOne deliberate independent observation of a task and static configuration under a repeat plan, distinct from every transport invocation, semantic retry, and provider attempt.
Repeat IDThe stable identity of one repeat slot in a repeat plan, identified by task identity and index; an optional RNG seed is slot data associated with the observation, never part of the slot identity and never a retry attempt number.
Repeat PlanA deterministic ordered plan enumerating a fixed count of repeat slots for each selected task identity; its identity covers the task identities and count but excludes per-slot seeds.
Sampling DefinitionA versioned, variable-bearing definition that declares task set and repeat plan variables and materializes a sampling config.
Sampling ConfigA complete validated config materialized from one sampling definition, naming a task set and repeat plan identity; its definition reference and identity hash identify its owner.
Preprocessing DefinitionA versioned, variable-bearing definition that declares ordered preprocessing steps and materializes a preprocessing config, resolving each step's version from the registry so a step version bump changes the config identity even when the step list is unchanged.
Preprocessing ConfigA complete validated config materialized from one preprocessing definition, whose identity folds in the resolved step versions; its definition reference and identity hash identify its owner.
Metric QuestionOne declared metric family bound to a trace key with settings, resolved to an operator version at materialization, determining a single extraction operation within a metric extraction definition.
Metric Extraction DefinitionA versioned, variable-bearing definition that declares ordered metric questions and materializes a metric extraction config, resolving each operator's version from the registry.
Metric Extraction ConfigA complete validated config materialized from one metric extraction definition, whose identity includes the resolved operator versions; its definition reference and identity hash identify its owner.
Evaluation Procedure DefinitionA versioned, variable-bearing definition that composes a preprocessing config and a metric extraction config with failure-semantics variables and materializes an evaluation procedure config.
Evaluation Procedure ConfigA complete validated config materialized from one evaluation procedure definition, whose identity folds in the component config identities and hence the resolved operator and step versions; its definition reference and identity hash identify its owner.
Aggregation DefinitionA versioned, variable-bearing definition that declares reduction, missing-data, and zero-denominator variables and materializes an aggregation config.
Aggregation ConfigA complete validated config materialized from one aggregation definition; its definition reference and identity hash identify its owner and its assignment drives aggregation.
Eval DefinitionA versioned, variable-bearing composite definition that declares sampling config, evaluation procedure config, and aggregation config variables and materializes an eval config.
Eval ConfigA complete validated composite config materialized from one eval definition; its identity hash covers all three component config identities.
Python SourceThe role of a text value read as Python source; a thin typed wrapper that records the interpretation without asserting the source compiles.
Code CandidateOne Python source candidate at a stable ordered position with its extraction lineage, carried as a typed value rather than a bare string.
Code Candidate SetA present ordered collection of zero or more code candidates with aligned positions and lineage; an empty set means preprocessing ran and no candidate survived, which is a valid outcome and not a failure.
Code ArtifactA Python source value validated by a compile check at construction, so source that does not compile cannot inhabit the type; the source string is canonical and the parsed view is derived on demand.
Operator LineageThe resolved operator and step version identity attached to a metric fact, plus the evaluation procedure config identity, so a measured value traces to the exact extraction operator and step that produced it.
ApplicabilityThe explicit applicable or not-applicable state carried by a metric fact, kept distinct from a measured value of zero and from an operator failure.
Metric FactA measured named value with an explicit unit, an applicability state, and operator lineage.
Metric RecordThe answer to one metric question, carrying its own status and exactly one of: one or more metric facts, an explicit not-applicable state with an absence mode and cause, or an operator-failure state with a type and message.
ScoreA named value deterministically derived from metric facts under one evaluation procedure config, retaining the config identity and the source fact names it was derived from.
Compression Reference ArtifactAn immutable byte value used as a compression denominator, whose identity is the hash of its bytes and which is independent of any dataset field or experiment-specific selection rule.
Compression Reference KeyA stable typed key that resolves to one compression reference artifact; an unbound key resolves to an explicit error rather than a default, distinct from a resolved but empty artifact.
Aggregation OutputThe deterministic result of applying one aggregation config to an explicitly complete input collection, carrying a numeric value, an explicit status covering missing-data, not-applicable, and zero-denominator outcomes, and the contributing counts, with no lifecycle result, authority, orchestration, objective, or reward semantics.

Guarantees

Definition-Owned Configs, Each Carrying Its Full Identity. A config is only ever built by materializing exactly one definition, and it carries that definition's reference plus its own full identity hash, so a config always names the exact definition and identity it came from.
  • Materializes a config only from a complete validated assignment of every required variable, filling defaults and rejecting unknown, missing, or out-of-range values.
  • Computes the identity hash as the full 64-character lowercase SHA-256 hash over a caller-selected payload of finite JSON-safe fields.
  • Folds resolved operator and step versions into the metric extraction and evaluation procedure config identities, so a version bump changes identity even when the declared question or step list is unchanged.
  • The eval config identity hash covers all three component config identities.
  • Rejects Python source that does not compile at code artifact construction, so invalid source cannot inhabit the type.
  • An empty code candidate set is a valid outcome, never treated as a preprocessing failure.
  • Requires an explicit unit on every metric fact and score, and keeps applicability distinct from a measured value of zero.
  • A metric record populates exactly one of measured facts, an explicit not-applicable state, or an operator-failure state.
  • Returns the explicit zero-denominator sentinel rather than dividing by zero, and never coerces it to a number.
  • Treats an optional RNG seed as repeat slot data, never part of a repeat ID or repeat plan identity.
  • Aggregation is a pure deterministic function over an explicitly complete input collection: the same config and same ordered inputs always produce the same output, with no lifecycle, authority, orchestration, objective, or reward semantics.

In vs. Out of Scope

In scopeOut of scope
  • The six definition and config pairs and their identity hashes
  • Dataset-specific task identities, task set manifests, and repeat plans
  • Typed code candidates and compile-valid code artifacts
  • Metric facts, records, and derived scores
  • Generic compression reference keys and artifacts
  • Pure aggregation outputs
  • Experiment policy and authority
  • Optimization, objectives, and rewards
  • Orchestration and scheduling
  • Dataset field selection and experiment-specific reference rules
  • Storage and persistence of results
  • The canonical JSON rendering and hashing mechanism itself, owned by the storage layer

Exported Names

Each row maps a term, or a group of supporting exports, to names in dr_code.eval.__all__. Every exported name appears exactly once in the names column; there are no aliases or alternate spellings. The definition, config, variable, materialize, payload, lineage, and unit rows name concepts carried by the typed exports below rather than exports of their own. Rows follow Terms order, with the zero-denominator sentinel row placed beside the outputs that return it and the identity hash row last as the storage boundary shared by every definition and config.
